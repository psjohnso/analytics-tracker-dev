Behavior notes & what the build covers
Design intent locked in, ready for review before code goes in.

Behavior summary

  • Approach A · Close-time modal. Intercepts every project status change to Complete or Canceled. If the project has open child tasks, the modal opens with them pre-listed. Apply is disabled until every task has a resolution (Complete / Cancel / Transfer). After Apply: batch task updates → project status update → status-history entries written on each affected task with reason "parent project [X] [Completed/Canceled]".
  • Approach B · Settings hygiene widget. Surfaces existing orphans (open tasks whose parent project is closed). Groups by parent so the context is clear. Each "Resolve these N" button opens the same modal preloaded with that group's tasks.
  • Default behavior differs by parent status. Canceled project → every row defaults to Cancel (one-confirm flow, fast). Complete project → no default (deliberate per-task choice required).
  • Transfer flow. Searchable picker, only Active / On Hold / Scheduled projects shown. On Apply, the task's project_number FK gets re-pointed; task_number stays as-is. Past time entries keep their original project_id (historical truth), future time goes to the new project.
  • Notifications. When the cascade auto-changes a task's status or transfers it, a notification is written to its assignee so they hear about it.
  • Audit trail. Status history entries note the parent action that triggered the cascade. Transfers note both old and new project numbers. Visible on the task detail page's status history strip.
  • Re-opening a closed project. Does not reverse the cascade. Tasks that were auto-canceled or auto-completed stay that way. Manual restore from each task's detail page is the path.
  • Permissions. Close-time modal: anyone who could close the project. Settings widget: admin-only.

What ships in the commit

  • One shared modal component — opens with a list of tasks + a "parent context" describing what triggered it. Used by both Approach A and B.
  • Hooks at every project-status-change entry point — the markProjectComplete button on the detail page, the status dropdown on the project detail, bulk actions that include status changes. Each one checks for open tasks before applying.
  • Settings → Project hygiene section — admin-only, lives in the Project Config group.
  • Status history + notifications integration — leverages existing tables; no new schema.

No AGOL schema changes. ~400 lines of new code (one new modal file + integration points + Settings panel). One commit.
