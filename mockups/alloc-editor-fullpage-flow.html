Interaction details worth pinning down:
  • URL pattern. Mock uses /resources/<member>/edit-allocations. The app is a single-page SPA, so this is hash-routed under the hood (#/resources/member-b/edit-allocations) or a query-param variant. Either works; routing convention is a one-line decision.
  • Return path. Three ways out: Cancel button, breadcrumb link, browser back. All three land on the same Resources state. If there are unsaved edits, intercept all three with a "Save changes?" confirm.
  • Switch member sidebar. The right-sidebar widget lets a lead edit Member A → Member B → Member C without bouncing back to Resources. Clicking another name auto-saves the current edits (or prompts) and loads the next person. Optional — drop if it complicates the data model.
  • State preserved on return. Same selected member, same scroll position, same filters. Implemented as: Resources tab keeps its UI state in module-level vars (already does); the route change preserves it because we're not re-mounting the Resources component.
  • "Allocations updated" confirmation. Optional little chip in the member-detail header showing what just happened. Auto-dismisses after ~5s.
  • What replaces the modal? The current modal-open code path (openAllocEditor()) becomes a router push instead of a modal show. The actual grid rendering can be largely shared between the two if you want a transition period where both work.

If the switch-member sidebar feels like scope creep, drop it for v1 and just route back to Resources between members. Easy to add later. Otherwise, ready to prototype this — want me to start with the route + shell + sidebar, with the grid markup just imported from the existing modal?
