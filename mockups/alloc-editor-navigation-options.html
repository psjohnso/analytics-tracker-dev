Allocation editor — navigation alternatives

Three more-distinctive ways to surface "you're in the editor, here's how to leave" than the current breadcrumb. Same browser frame and same editor body in each panel so the focus is on the nav element.

Option 1
Prominent back banner
Replaces the subtle breadcrumb with a navy banner running the full width of the editor. A button-styled "← Team Resources" on the left is unmistakable. Member name appears as a large title; Cancel/Apply on the right.

Pros

  • Impossible to miss — colored banner runs full width with a clearly-buttoned back affordance.
  • Member name reads as a large page title, reinforces context.
  • Cancel/Apply visually grouped with back action.
  • Maps cleanly to common app patterns (Linear, GitHub PR editor).

Cons

  • Adds vertical real estate (~50px) above the editor.
  • The navy banner is heavy visually — pulls the eye away from the grid.
  • Color competes with the app header; some designers would call this redundant.
Option 2
Mode toggle pill
A two-option toggle ("Team Summary" / "Edit · Member B") shows the modes as equal peers. Clicking either chip switches view. Member context lives next to the toggle. Click "Team Summary" to leave the editor.

Pros

  • Two-state design makes both directions feel "first-class" — Team Summary isn't a back action, it's a peer view.
  • Lighter visual weight than the banner; doesn't compete with the app header.
  • Pill toggle is a familiar pattern (already used elsewhere in the app for chart/table, unit filters).
  • Clicking "Team Summary" is one click; same as a back button.

Cons

  • Less "I am editing right now" tension — the toggle reads more like a calm choice between two views.
  • Two-mode framing is slightly more abstract than a back button (users have to understand it's a toggle).
  • If we ever add a third mode (e.g., "Notes"), the pill stops scaling cleanly.
Option 3
Persistent member rail + content tabs
Member list stays pinned on the left at all times. Content area to the right has two tabs ("Summary" / "Edit Allocations") that switch the view for the currently-selected member. Click any member in the rail to switch person; the active tab stays. Lets a lead edit Member A → B → C without ever leaving the editing layout.

Pros

  • Most powerful for the unit-lead workflow — edit Member A, click Member B in the rail, edit, click C, etc., never leaving the editing layout.
  • "Summary" / "Edit Allocations" tabs make both modes equally first-class, like Option 2 but more spatial.
  • Resources is no longer "the page you leave to edit" — it's a tab within a richer member workspace.
  • Selected member is always visually highlighted in the rail; never lose context.

Cons

  • Biggest architectural shift — the Resources tab itself needs to be re-organized around this rail+pane layout.
  • Save semantics get fuzzier when clicking another member with unsaved edits (auto-save? prompt?).
  • Smallest grid area of the three options (the member rail eats ~220px on the left).
  • Most engineering work — likely 1–2 days of refactor.

How to choose between them. The right answer depends on the primary user persona:

  • If team members editing their own allocations is the main flow → Option 1 (back banner) is the cleanest. It says "you're doing one focused thing, here's how to leave." Single-purpose, single-direction.
  • If unit leads doing reviews (going back-and-forth between summary and edit, sometimes for the same person twice) → Option 2 (mode toggle) wins because the toggle makes it cheap to flip views.
  • If unit leads editing multiple members in a session → Option 3 (member rail) is decisively better because you never leave the editing layout. The whole "navigate-back-then-pick-next-member" overhead disappears.

My instinct: Option 1 ships fastest with the biggest "distinctiveness" win over what's currently there. Option 3 is the right long-term direction if you expect lead-review workflows to grow. Option 2 is the smallest delta from today's design.
